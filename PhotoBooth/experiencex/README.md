ExperienceX is isolated from Experience: its executable, mutex, logs, and default UDP port are distinct. Camera and ExperienceX use UDP 54242 for events and UDP 54243 for commands; ExperienceDeviceName selects the receiving computer alias or hostname. No C++ rewrite is required for this prototype.

See [ARCHITECTURE.md](ARCHITECTURE.md) for source organization, thread/resource ownership, configuration migrations, shutdown, and test suites.

Video screens accept `command:"fadeOut"` and `command:"fadeIn"` with required `durationSeconds`. They fade to transparent or back to full opacity, revealing the configured display background and lower layers while playback continues. Screen opacity holds until the next fade command, including across new videos and loops. Use existing screen/wildcard/role targets; media-bound screens support these commands too. Chroma key and ordinary playback transitions remain independent. Existing priority arbitration still applies. See [the protocol](../NETWORKING.md#video-screen-fades).

Command-line example: `./Send-Experience.ps1 -Device '*' -Command fadeOut -DurationSeconds 1.5 -Screen 'Projector/screen1'`. Use `-Command fadeIn` to restore visibility; `-Roles 'Front'` can replace `-Screen`.

Video play requests accept `playbackSpeed` from 0.5 to 2.0 (default 1.0). It uses the native media engine without frame interpolation or additional shader passes. Eligible same-video requests update speed in place, preserving position and looping. Fades use real seconds, and Controller's duration estimates account for speed. Speed is per request; an omitted value restores normal playback. Example: `./Send-Experience.ps1 -Value 'Ghosts/Ghost2.mp4' -Screen '*' -PlaybackSpeed 0.5 -Loop`. Media-bound screens retain their existing command lock. See [playback speed](../NETWORKING.md#video-playback-speed).

The roles list in new/edit screen properties combines local screen/audio assignments with role names from all playlists shared by local and discovered peer Controllers, including playlists not attached to a scene. Names are sorted and deduplicated without case; exclusion targets contribute their bare name, and wildcards are omitted. Existing assignments remain checked, other suggestions start unchecked, and **Add** still accepts manual names. Role suggestions update through the normal local Controller catalog and are cached for restart/offline use.

Controller reannounces active playlist loop commands every **15 seconds**. An unchanged request for a currently playing loop is logged as `VideoLoopAlreadyPlaying` and ignored, preserving decoding, position, opacity and the original playback request ID. A speed or mute change still applies without restarting. Late-starting/restarted Experience instances can pick up playback from a later announcement. Existing local-media requirements, media locks, fades, priority conflicts and remembered background resumption still apply.

Priority-blocked video requests broadcast `playback.priorityRejected` events for
Controller's activity feed. Entries identify the video, Experience device,
display/screen and requested versus active priority. A remembered background loop
is labeled **Deferred**; a rejected one-shot is **Ignored**. Events retain the
original request and scene/playlist context, and use background UDP transmission
so rendering never waits for the network. Screen-name media locks and unavailable
outputs are separate conditions and do not generate this event.

Configuration rendering caches stationary outlines, grids and labels in cropped per-screen textures. Animated points use small local draw regions, and one shared overlay texture per display refreshes at 30 FPS. Video presentation keeps its existing cadence; editing commands force an immediate overlay refresh. Selection order, glow colors, flashes, LED sampling guides and HUD placement are preserved. Caches resize with the display and release when no overlay is visible.

`ExperienceX.Tests -- --calibration-performance` compares GPU pixels against the previous shader (test fixture only), checks cache invalidation and immediate edits, and records a 16-screen overlay-only GPU benchmark in `.tools/calibration-benchmark.json`. This measures overlay work, not decoder capacity or end-to-end video FPS. The mixed editing/playback soak is `--renderer-soak`.

## UDP commands

Broadcast one UTF-8 JSON object per datagram to IPv4 UDP command port **54243**; events use **54242** (configurable), up to 1200 bytes. Every message requires `device`, `source` and a unique `requestId`. `device` is the destination computer's configured `DeviceName`, falling back to its hostname; `*` explicitly targets everyone. Matching ignores case and surrounding whitespace. Missing destinations are rejected. Commands are anonymous, without authentication or acknowledgements. Delivery is best effort. See [the shared networking guide](../NETWORKING.md) for events, configuration and migration.

Retries with the same `requestId` and logical `source` are suppressed for `RequestDeduplicationSeconds` (default 60), even when sender IP or port changes. Use a new ID for each distinct command, including commands for different displays/channels. The bounded cache holds at most 4096 IDs; restarting clears it. Requests later rejected for unavailable media/outputs require a new ID to try again. Retention must cover RequestLifetimeSeconds. Our senders make three identical attempts 75 ms apart and include a ten-second local processing budget. Default messages do not require synchronized clocks. The application sends no UDP replies.

```json
{"device":"projection-pc","source":"controller","requestId":"use-a-new-unique-id","experience":"video","value":"ping.mp4","displayName":null,"mute":false}
```

```json
{"device":"projection-pc","source":"controller","requestId":"use-a-new-unique-id","experience":"video","value":"ping.mp4","screen":"Projector/screen1","mute":true}
```

```json
{"device":"projection-pc","source":"controller","requestId":"use-a-new-unique-id","experience":"audio","value":"sound.mp3","audioDevice":null,"channel":1,"volume":35,"mute":false}
```

`displayName` omitted/null/empty uses `DefaultDisplayName`; an empty default selects the primary display. `audioDevice` omitted/null/empty uses `DefaultAudioDevice`; an empty default selects the system multimedia audio output. Audio devices accept an exact friendly name (case insensitive) or endpoint ID. Duplicate friendly names are rejected; use their IDs. A missing display is rejected without falling back. Missing audio outputs are logged and skipped; a request with no available outputs is rejected. Requests are not queued for reconnection.

### Coordinated audio and virtual devices

Send one audio request to any subset of outputs. Prefer the `audioDevices` array, especially when friendly names contain commas:

```json
{"device":"projection-pc","source":"controller","requestId":"use-a-new-unique-id","experience":"audio","value":"sound.mp3","audioDevices":["Device A","Device B","Device C"],"volume":60}
```

`audioDevice:"Device A,Device B"` also accepts a comma-separated list. A whole exact physical name is resolved before splitting, preserving names containing commas. Use either `audioDevice` or `audioDevices`, not both. The request's channel, volume and mute apply to every selected output. Duplicate endpoint IDs reached through different names/groups play only once per request. Up to 32 distinct outputs are supported.

Use `"audioDevice":"*"` (or `"audioDevices":["*"]`) to play on every currently active physical audio output on the receiving Experience computer. `"device":"*"` broadcasts this to all Experience computers. The output inventory is resolved for each new request; newly connected devices participate in the next request. `DefaultAudioDevice` may also be `"*"`; this name is reserved and cannot name a virtual device group. Stereo/multichannel source audio is averaged for mono endpoints. Requests with no active outputs are logged and skipped. Multi-output requests retain the shared decoder, coordinated start and overlapping-track behavior described below.

Define virtual audio devices in the current user's local configuration:

```json
"VirtualAudioDevices": {
  "Room": ["Device A", "Device B", "Device C"],
  "Front": ["Device A", "Device B"]
},
"DefaultAudioDevice": "Room",
"AudioDeviceLatencyMilliseconds": {}
```

Replace these placeholders with physical endpoint IDs or exact friendly names from the log. Then send `{"device":"projection-pc","source":"controller","requestId":"use-a-new-unique-id","experience":"audio","value":"sound.mp3","audioDevice":"Room","volume":60}`. Virtual names ignore case/outer whitespace and can also appear in `audioDevices`. These are application groups, not Windows audio devices. Members must be physical names/IDs; nested groups are rejected. Names must not conflict with physical devices. Membership/default changes reload automatically and affect new requests; an existing request keeps its selected devices. No real devices are assigned to groups automatically.

All available selected endpoints are prepared before a common future media start. Multiple outputs share one decoder and bounded PCM history, with separate shared-mode WASAPI streams. Endpoint clock/QPC timestamps align playback against one timeline; band-limited resampling gently corrects clock drift. Separate grouped requests can overlap on the same speakers. Missing, disconnected, invalid-channel or failed outputs are logged and skipped while other selected outputs continue. If none remain, playback is rejected or ends with a failure. A reconnected output does not join an existing request.

Different speakers can add processing delays that Windows does not report. `AudioDeviceLatencyMilliseconds` maps a physical endpoint ID or friendly name to its measured **additional downstream latency**, from 0 to 5000 ms. IDs take precedence over names. For example, `{"Device B":25}` schedules Device B's samples 25 ms earlier relative to the other outputs. This compensation is captured when a coordinated request is prepared. Measure/test the speakers at the intended listening position; software clock alignment cannot guarantee sample-perfect acoustic alignment across unrelated hardware. Group startup includes roughly 300 ms of preparation lead, plus the largest configured downstream latency. Synchronization logs report endpoint-clock/cursor error, estimated clock drift, and underruns, rather than claiming acoustic measurements.

Use a new requestId for each intended action; projection-pc is a placeholder device alias.

```powershell
./experiencex/Send-Experience.ps1 -Experience audio -Value sound.mp3 -AudioDevices 'Device A','Device B' -Volume 60
./experiencex/Send-Experience.ps1 -Experience audio -Value sound.mp3 -AudioDevice Room -Volume 60
```

### User-managed display aliases

Edit `DisplayAliases` in the local `appsettings.json` described below. For example (assign the Windows names to match your actual layout):

```json
"DisplayAliases": {
  "Left": "\\\\.\\DISPLAY2",
  "Center": "\\\\.\\DISPLAY1",
  "Projector": "\\\\.\\DISPLAY3"
},
"DefaultDisplayName": "Center"
```

Then send `{"device":"projection-pc","source":"controller","requestId":"use-a-new-unique-id","experience":"video","value":"ping.mp4","screen":"Projector/screen1"}`. Alias names ignore case and surrounding whitespace. Raw Windows display names still work. Changes reload through the configuration file watcher; they apply to new requests and do not move existing playback. Unknown aliases and disconnected targets are logged and rejected without fallback. Aliases must have unique nonempty names and nonempty targets; aliases reference Windows display names directly, not other aliases. The example map uses Projector=DISPLAY2, Display One=DISPLAY1, and Display Two=DISPLAY3. Shipped defaults have no aliases; configure the assignments for each PC. Windows display numbering can change after hardware/connection changes; update the map if that happens. This map does not rename displays in Windows or bind to hardware serial numbers.

Channel numbers start at **1**, in the selected device's configured Windows channel order (normally 1=left, 2=right). A specified channel receives the source channels averaged to mono; other output channels are silent. Omitted/null `channel` retains the source channel ordering; mono is duplicated to front left/right and stereo occupies the first two channels. A source with more channels than the device is rejected unless an explicit channel is supplied. Configure multichannel devices with the desired channel count in Windows. Audio is resampled to the endpoint rate when necessary.

Video playback is independent per screen; a new video replaces only the previous video on the targeted screen, unless that screen is bound to media by its name. Other screens on the same display continue playing. Each standalone audio request plays independently, including multiple tracks on the **same audio device and channel**. Windows mixes their shared-mode streams. Each track keeps its own volume, mute and fades. Use a distinct `requestId` for each intended track; retrying the same ID still suppresses duplicates.

### Media-bound screen names

Name a video screen after a file in the local `VideoDirectory` to keep that media playing automatically. For example, `Eye` binds to `Eye.mp4` and loops it with muted audio; `Skull` binds to `Skull.png` and holds the still image. Matching ignores case and does not require the extension. The screen fades in once; videos do not fade between repetitions. Images retain their alpha transparency and use the same points, stretch rendering and black chroma-key settings as video.

A matching name locks playback: targeted commands, broadcasts and stop commands cannot replace or stop the content. Other screens and independent audio remain controllable. Point editing, resizing and renaming remain available. Rename to a name without a matching file to stop automatic playback and unlock commands. Mat screens never bind to files.

The local folder is checked every second, so media arriving after startup, updated files and removed files apply automatically. Unrelated configuration edits do not restart bound playback. Failed playback stays locked and retries after five seconds. Bound content resumes when its display or graphics renderer recovers. Images are decoded/uploaded once and do not continuously render after their fade completes. No network file is used for playback.

If multiple files share the same basename, the screen stays locked and blank and logs `ScreenMediaBindingAmbiguous`; include the extension (for example `Eye.mp4`) to select one. Video extensions: MP4, M4V, MPG, MPEG, WMV, AVI, MOV, TS and M2TS, subject to the installed Media Foundation codecs. Still images: PNG, JPG/JPEG, BMP, GIF and TIF/TIFF; GIF uses its first frame. Files must be directly in the media folder. Binding, playback and ignored commands are recorded in telemetry. Verify with `ExperienceX.Tests -- --screen-media`.

Audio `volume` is a numeric percentage from **0 to 100**, including fractional values. Omitted/null defaults to **100**. It scales that track's samples before mixing and multiplies its fades; `mute:true` overrides volume. Zero volume still advances playback until the natural media end. Invalid volumes are rejected. This controls standalone audio requests; video's embedded sound remains enabled unless `mute` is true and uses the normal video audio output. `mute` defaults to false for both experience types. Neither setting changes system volume or another track's volume. Overlapping loud tracks add together, so lower individual volumes when needed to avoid distortion.

There is currently **no stop command**. Playback finishes at the file's natural end. Required `requestId` and `source` are carried into telemetry. Malformed requests, unsupported experience names, unavailable files, and invalid channels are rejected without replacing valid playback. Files must resolve inside the configured media directory; URL and rooted-path requests are rejected.

Use a new requestId for each intended action; projection-pc is a placeholder device alias.

```powershell
./experiencex/Send-Experience.ps1 -Value ping.mp4
./experiencex/Send-Experience.ps1 -Value ping.mp4 -DisplayName '\\.\DISPLAY2' -Mute
./experiencex/Send-Experience.ps1 -Experience audio -Value sound.mp3 -AudioDevice 'Speakers (USB Audio Device)' -Channel 2 -Volume 35
```

### Display backgrounds

`DisplayBackgrounds` maps a configured alias or raw Windows display name to separate `BackgroundColor` and `IsTransparent` values. `BackgroundColor` is an opaque `"#RRGGBB"` color; `IsTransparent` controls whether the background is visible. Newly detected displays are created and saved with black (`#000000`) and `IsTransparent:false`, including on startup and hot-plug. Existing settings are preserved. For example:

```json
"DisplayBackgrounds": {
  "Projector": { "BackgroundColor": "#000000", "IsTransparent": false },
  "Display One": { "BackgroundColor": "#000000", "IsTransparent": true },
  "Display Two": { "BackgroundColor": "#000000", "IsTransparent": false }
}
```

Each background fills the entire display, including outside the keystone quadrilateral and video letterboxing. It stays visible while idle, during video fades, and through black-keyed video pixels. Only the video fades; solid backgrounds remain opaque. Rendering composites video over the background on the GPU. Background transparency is independent of chroma key and video fading. Alias, color and transparency edits reload immediately without restarting or interrupting playback. Removing an entry recreates black/opaque defaults when the connected display is detected. Each display can have only one entry (do not configure both its alias and device name); invalid colors or ambiguous targets reject the edit and retain the last working settings. Unplugging a display still hides its window. Solid backgrounds remain topmost while idle; transparent idle windows retain the existing behavior.

Configuration version 2 migrates legacy background strings while preserving their appearance: `"transparent"` becomes black plus `IsTransparent:true`; a solid color becomes that color plus `IsTransparent:false`. Migration is atomic, backs up the old file, and preserves keystones and unknown settings. Legacy string edits are still accepted and converted; use objects for new configuration.

## Configuration

**Copy and paste screens:** select a video/image or mat screen and press **Ctrl+C**, then point to the destination display and press **Ctrl+V**. Each paste creates and selects a new screen with a unique ID, a unique name (for example `Eye-2`) and its own default screen name. Points retain their normalized positions, including across displays. Perspective, zoom/pan, brightness, roles, chroma-key settings, bound relative media path and normal/negative mat mode are preserved. The copy is inserted above the highest screen of its type using the usual creation order. Bound media plays independently on the new screen, using the destination's local media. The clipboard contains saved screen settings, not the media file or a running command's playback state. Repeated pastes are queued in order. G-Force and LED output screens cannot be duplicated this way. Normal text copy/paste remains available while editing a name or dialog; screen shortcuts are released outside configuration mode and when another app has focus. Clipboard failures appear as a notice and log entry. Configuration saves atomically and existing screens stay unchanged. Verify with `ExperienceX.Tests -- --screen-copy`.

**Initial points do not snap:** full-display corners at `(0,0)`, `(1,0)`, `(0,1)` and `(1,1)` remain independent across screens, even when their coordinates match exactly. The centered one-third-size default corners remain independent too. These initial positions are excluded as join targets, so a newly created screen's point can leave a corner without pulling other screens or snapping back. Moving an initial edge affects only its screen. Initial LED-array endpoints at `(0,0.5)` and `(1,0.5)` behave the same way. Edited points away from those initial positions retain exact-coordinate grouping, explicit J joining, undo and Delete-to-disconnect behavior. The rule is derived from coordinates and survives restart without extra configuration.

**LED screens:** use **A,L** in configuration mode, choose a Controller array/matrix perspective, then position the line or rectangle. Live guides are excluded from sampling. Controller discovers WLED and defines whole segments, dimensions, per-perspective FPS (default 30) and array thickness (default 10% of the larger display dimension). See [LED setup, configuration and tests](Lighting/README.md). Updated installers include mDNS UDP 5353. Existing media, mat and G-Force shortcuts remain available.

**Negative mats:** **A,M** creates a normal mat (hides media beneath it inside its polygon). Press **M** again while the mat is selected to toggle negative mode (hides media outside, retains it inside); **A,M,M** works even when entered quickly. Further M presses alternate between the two modes. The screen's `IsNegative` setting saves immediately and reloads live, preserving points, name and layer order. A full-display negative mat initially covers nothing; move its points or add points by double-clicking edges to shape the opening. Its layer position determines which content it masks, just like a normal mat. This does not change the separate inverse mask owned by G-Force. M is inactive outside configuration mode or while typing a name.

**Video framing:** the A,V creation dialog still includes name, roles and perspective; P still changes the selected perspective. In configuration mode, select a video/image screen and scroll over its interior: up zooms in around the pointer, down zooms out. Each wheel notch changes zoom by 10%, within 1–100x. At 1x the entire selected perspective fills the screen; an unassigned perspective means the entire source. Ordinary dragging moves the screen as before. Shift+drag inside the selected video screen pans its media behind the unchanged screen points. Panning stops at the selected perspective's edges and cannot expose blank space. At 1x there is no room to pan. Point and edge editing retain their ordinary gestures.

Without a wheel, hold **Ctrl** while pressing the left mouse button over the video, then move up or right to zoom in, down or left to zoom out. Zoom stays anchored at the initial click. Horizontal and vertical travel combine: 200 logical pixels right/up doubles zoom; equal opposing movement cancels out, with DPI scaling, and release saves the result. Ctrl takes precedence if Shift is held too. **Shift+drag** continues to pan the video behind the fixed screen/mat boundaries. **Ctrl++ / Ctrl+=** and **Ctrl+-** zoom by one wheel step; **Ctrl+R** resets the selected video/image screen to 1x centered media, 100% brightness, full perspective and application-default chroma key. It saves all those settings together, preserving screen points, name, media binding, roles and layer order. Plain **R** resets screen points. Numpad +/- equivalents work too. Keyboard zoom uses the pointer as its anchor when inside the selected screen, otherwise its center. Plain +/- still adjust brightness. Keyboard zoom is released while editing text, while another application has focus and outside configuration mode; drag zoom/pan only operate in configuration mode. Lost mouse capture or conflicting remote settings cancel an unfinished drag.

**Without a mouse button:** while a video/image screen is selected, put the pointer over it and hold **Shift** while moving to pan, or hold **Ctrl** while moving up/right to zoom in or down/left to zoom out. Release the modifier to save; **Escape** cancels. A compact azure HUD at the bottom of the display shows shared Screen controls first on the left, followed by media Movement and Video controls. Selected mats use the same Screen column followed by Mat controls (M for normal/negative and double-clicking an edge to add a point). Groups wrap on narrow displays. It omits clipboard shortcuts and save/cancel notes, and submenus temporarily hide it. These gestures start only while Experience has focus, no mouse button or other key is held, no name/dialog is being edited, and no point movement is pending. Combined modifiers and other shortcuts block a new gesture until the modifiers are released. Losing focus, changing selection or conflicting remote edits cancel an unfinished gesture. Existing mouse-button, wheel and keyboard zoom controls remain available.

**Media rotation:** hold **Alt + move** over the selected video/image screen to rotate its media. Right/up rotates clockwise, left/down counterclockwise; 200 logical pixels of combined travel makes a quarter turn. The screen's points remain fixed. Rotation preserves pixel proportions using the average screen edge lengths, including on rectangular displays. Uncovered areas are transparent, and pixels outside the selected perspective are never shown. Zoom can fill exposed corners; zoom and movement follow the rotated media. Release saves, Escape or losing focus cancels. The Movement HUD reads “Hold Shift + move: move media”, “Hold Ctrl + move: zoom media” and “Hold Alt + move: rotate media”. Ctrl+R also resets rotation to zero.

**Video outlines:** double-click an edge in configuration mode to add a point, using the same controls as mats. Added points define a clipping outline and can form concave shapes; they do not add distortion anchors. The original four points retain the existing keystone mapping. Moving an added point outward automatically expands the media coverage horizontally or vertically. For an outline with extra points, rotation also applies enough minimum zoom to keep its interior covered; chroma-key and source-image transparency still work. Points save immediately after insertion or a completed movement. ## Transparency and keystone

Screen chroma key and display background transparency are independent. A video screen can include its own `BlackKey` object (`Enabled`, `Threshold`, `Softness`); absent/null uses the application's root `BlackKey` defaults. K creates a screen override using the current threshold and softness, then toggles only its enabled state. Remote edits to screen overrides apply live. Keyed video pixels reveal underlying screens or the display background; the desktop is visible through them when the display background is also transparent. B controls the entire window background, including outside every screen's points. No shader compilation is needed when changing these settings.

`BlackKey.Enabled` defaults to true. The final video surface, including letterboxing and keystone backing, is keyed by a pixel shader. `Threshold` (default 0.015) removes colors whose brightest RGB channel is at or below that value; `Softness` (default 0.03) softens the edge. Values are normalized 0â€“1 and must total at most 1. Lower values retain more dark detail. Production mode gives a borderless transparent surface; developer mode retains normal window chrome. The same shader multiplies premultiplied color and alpha for fades while native window opacity stays at 1, keeping the media render path active even at zero visible alpha. Disabling black key bypasses color removal while retaining shader fades. The compiled Direct3D shaders are embedded; normal builds need no shader compiler. Use `Compile-Shaders.ps1` after editing HLSL.

## Fullscreen visualization

In configuration mode, **A then G** creates a `visualization` screen named `gforce` (`gforce2`, etc. if that name is already reserved) on the selected screen's display, or the default display when nothing is selected. SoundSpectrum **G-Force Standalone must be installed separately**. Experience finds the installed x64 executable automatically; `Visualization.ExecutablePath` can override its location (environment variables are expanded).

This version supports **one visualization per Experience instance**. A single fullscreen instance passed local tests on the primary and a non-primary display; simultaneous fullscreen instances did not. Delete the existing visualization before creating one elsewhere. Video and mat screens remain independent and can run on every display.

G-Force runs as an owned external process in its actual fullscreen mode. Its normal render window first establishes the assigned display without activation, then Experience requests fullscreen over its owned local TCP control connection, with no global keyboard injection. Experience keeps its media layers above G-Force; mat cutouts reveal the visualization underneath. Chroma-keyed video pixels reveal the visualization, including any black details such as Eye.mp4's pupil. A visualization always covers its display: its name and selection are editable, and Delete removes it, but its external window remains fullscreen and its media binding, chroma key, brightness and source perspective are not editable.

Each visualization owns one inverse black mat, stored in the G-Force screen's Points. The window and this mat form the bottom pair; normal media and regular mats always draw above them, even after an external configuration reorder. The initial full-display polygon leaves everything visible. Black covers the area outside the polygon and the inside stays transparent to reveal G-Force. This adds one full-display GPU compositing pass and one reusable BGRA texture (about 8 MiB at 1920x1080), with no CPU frame copies or decoder changes. Displays without regular mats keep the direct rendering path. Resize and renderer recovery recreate the target; idle masks do not cause continuous rendering.

In Experience, drag a visible line to translate its two endpoints together without changing its angle or length. Endpoints already coincident with other normal screen points continue moving together. Corners take priority over lines; overlapping edges cycle through their screens. The effective display background is transparent while a visualization exists. Stored background settings are preserved and restored when it is deleted. Independently launched vendor processes are preserved. Launch, fullscreen readiness, failure, retries and shutdown are logged. This monitors process/window responsiveness; it does not measure G-Force's rendered-frame health.

## Looping video

Video requests accept `"loop": true`, default false. The [Media Engine's native looping](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaengine-setloop) repeats locally without reopening the decoder or restarting the fade-in. There is no fade between cycles. Loop-boundary smoothness still depends on the media and decoder; this does not promise gapless presentation.

Any request for the same local video on the same screen continues the existing decoder and playback position, including changes in request ID, mute or loop flags. A loop request enables looping without restarting the current pass; a one-shot never disables an existing loop. Distinct screens remain independent. `VideoPlaybackContinued` records decoder reuse. A higher-priority one-shot continuing a loop protects the current pass, then returns to Low background ownership at the next wrap.

Commands accept `priority: "low"`, `"medium"` or `"high"` (default Medium). Looping video always uses Low; `context.isAmbient: true` also implies Low. Controller sends all scene commands at Low and triggered storyboard commands at Medium. Video priority applies separately to each display/screen, including pending opens: lower cannot replace higher; equal replaces a different file. The latest background loop is remembered even while blocked, then resumes automatically when foreground playback finishes or fails. A failing background is not retried in a tight loop. Explicit playback stops clear matching background requests. Controller scene cancellation sends no stops; existing media remains subject to normal priority and background-loop behavior. Audio mixes at all priorities. Name-bound screens retain their existing lock behavior. `VideoRequestSkippedLowerPriority`, `VideoBackgroundRemembered` and `VideoBackgroundResumed` record these decisions.

### Screen and speaker roles

Every screen has a `Roles` property containing zero or more comma-separated names, for example `"Roles": "Entry,Scary"`. New screens default to `""`. Audio roles are configured in `AudioDevices`:

```json
"AudioDevices": {
  "{physical-endpoint-id}": { "Name": "Speakers", "Roles": "Entry,Scary" },
  "Room": { "Roles": "Ambient" }
}
```

Startup and the one-second audio inventory check add newly detected endpoint IDs with their descriptive `Name`. A newly detected Windows default audio output initially receives `Roles: "Subwoofer"`; other new outputs start with empty roles. If no default output is available, none is guessed. Existing entries, including explicitly cleared roles and disconnected-device assignments, are preserved. Changing the Windows default does not move roles on already configured endpoints. Edit `AudioDevices` to move or remove the Subwoofer role. Physical ID and friendly-name assignments combine. A configured virtual audio name such as `Room` adds its roles to that group's physical members. These `Name` values are descriptive; they do not rename Windows devices. Valid configuration edits update role matching and discovery inventories live.

```json
{"device":"*","source":"controller","requestId":"unique-role-request","experience":"video","value":"Eye.mp4","roles":"Entry,Scary","mute":true}
```

Roles match case-insensitively against **any** listed name, with one playback per matching output. Video selects video screens across all available displays; audio selects active physical speakers and uses the existing coordinated multi-output playback. Media must already be available locally. Direct screen/display/audio selectors cannot be combined with a nonempty `roles` target. Empty or omitted roles retain existing direct/default targeting. Unmatched roles never fall back to a default screen or speaker. Name-bound screens ignore role commands just like direct commands. Video priority and loop continuation apply normally; audio continues independently. `RolePlaybackNoMatchingOutputs` records unmatched role requests.

Role targets are ordered rules. Evaluate left to right: the first matching positive rule includes the output; the first matching `^name` rule excludes it. `*` matches everyone, including unassigned outputs; unmatched outputs are unselected. `"roles":"^subwoofer,*"` excludes subwoofers then includes the rest; `"roles":"*,^subwoofer"` includes everyone. `"roles":"Front,^subwoofer,*"` includes Front outputs even if also subwoofers, excludes other subwoofers, then includes the rest. `^*` denies everyone reaching it. Operators belong to targets, not assigned roles. Controller's random-speaker eligibility uses these same ordered rules.

```json
{"device":"*","source":"controller","requestId":"loop-playback-id","experience":"video","value":"ping.mp4","screen":"*","mute":true,"loop":true}
```

Controller automatically sends the following command when the owning scene changes. The sender must match the original playback's `source`; the stop has a fresh `requestId` and references the original in `playbackRequestId`. This stops only matching video instances across the receiving device, without depending on display/screen names that might have been edited. Audio and newer replacements continue.

```json
{"device":"*","source":"controller","requestId":"new-stop-id","experience":"video","command":"stop","playbackRequestId":"loop-playback-id"}
```

Stops use `TransitionOutSeconds` (currently three seconds), retain playback/decoding during the fade, and close only after a transparent frame is presented. Duplicate stops do not extend the fade. Stops received before their corresponding play are remembered for `RequestDeduplicationSeconds` in a bounded cache, preventing reordered requests from starting an already stopped loop within that window. Playback already replaced or stopped ignores a late stop. Use `Send-Experience.ps1 -Loop` for a standalone loop; Controller scene changes cancel unsent commands without stopping existing loops.

**Z** during a drag undoes the latest J join and suppresses reattachment until the point leaves the target's click radius; without a join it cancels the current drag. After saving, Z restores the whole linked edit from any affected screen. **Delete on a selected point** disconnects just that point and temporarily suppresses joining to its former peers until it moves outside their click radius. Point selection remains after mouse release; Delete on an unlinked selected point leaves the screen intact. Pending detachment is an editing-session behavior, not an additional saved configuration property. Holding and dragging a screen's interior remains independent screen repositioning.

With an ExperienceX window focused in configuration mode, click the screen interior to select the screen without a point, then Delete removes that screen and stops only its video. The removal is saved immediately; deleting the last screen leaves that display with zero screens, including after restart. Delete has no screen-removal action with nothing selected or while a name is being edited. A concurrent remote change to the selected screen cancels deletion rather than overwriting the remote edit.

The test grid and its center circle work without a video and follow the active correction. Display aliases, raw Windows name, resolution, normalized coordinates, and pixel positions appear on each display. Set `CalibrationGridEnabled` to false to hide the grid/readout while retaining corner editing. R resets only the selected screen to the identity rectangle with correction disabled and saves immediately. Z first cancels a pending draft; otherwise it restores and saves the previous local calibration for that display. Up to 20 confirmed local edits are retained in memory. Remote coordinate/enabled changes clear that display's undo history; restarting clears all undo history. A reset can therefore be undone immediately.

Remote configuration changes apply live. A change to the display being edited cancels its local draft so the remote coordinates win. Saving merges only that display's known fields into the latest configuration, preserving unrelated settings and other displays. The complete validated JSON is flushed to a temporary file in the same directory, then atomically replaces the original. `appsettings.json.bak` retains the previous valid file. Startup restores a valid backup when the main file is missing/corrupt and retains corrupt content in a timestamped `.rejected-*` file. Invalid or incomplete live editsâ€”including an empty fileâ€”retain the last valid settings until corrected, without overwriting the external edit.

The backup, lock, and temporary files are beside the local configuration. For coordinated read/merge/write, acquire `appsettings.json.lock` with `FileShare.None`, re-read the latest JSON while holding it, and release after replacement. Normal in-place writers are excluded during the application's merge; changed file replacements are checked and retried before commit. An uncoordinated external replacement can still race the final check, so cooperating writers should use the same lock.

An accepted remote calibration change also produces the local white confirmation flash around each changed corner on its own display, even with `configurationMode` off. An `Enabled`-only change flashes all four corners. Initial defaults, unchanged coordinates, and unrelated configuration changes do not flash. Local saves are not flashed twice when the file watcher reads their changes. `PointsRemoteChangeApplied` logs accepted remote changes; rejected configuration does not produce a success flash.

Success flashes wait for the renderer to acknowledge applying and presenting the expected geometry and for the settings to remain current. A failed renderer, superseded revision, or failed reload cannot produce a success flash. The acknowledgement times out after three seconds; rendering failures are logged. This confirms the renderer's submitted surface, not physical projector output.

Topmost enforcement raises without taking focus when playback starts/media opens, reacts to window-order changes, and checks once per second. It ignores cloaked windows and coalesces events; repeat successes are summarized in logs. This is best effort among desktop apps and does not cover secure desktops.

## Controller perspectives

### Direct G-Force control

Experience controls its owned G-Force Standalone directly over local TCP without the Toolbar. The `Visualization` configuration supplies explicit launch selections: `Theme: "(Standard)"`, `ColorMap: "Clear Blue Water"`, `WaveShape: "Random"`, `FlowField: "Random"`, `FlowFieldUnion: "None"`, `Particle: "None"`, and `Sprite: "None"`. Random chooses once from the active theme; automatic changes are always disabled for all six families and enforced every second. None disables the optional union, particle or sprite; core theme/palette/shape/field selections require a name or Random.

`TransitionSeconds`, `ChangeDelaySeconds`, `ParticleDurationSeconds` and `SpriteDurationSeconds` default to JSON `null`, preserving G-Force's behavior. Zero means immediate/zero explicitly. Times are seconds, from 0 through 3600. Configuration edits apply live; timing-only edits preserve the current selections. Invalid catalog names retain the existing running visualizer and are logged until corrected. Startup fills missing configuration fields while preserving supplied values. Experience owns fullscreen placement; there are no preset, script, overlay, screenshot, slideshow or interval command/configuration controls.

UDP commands use the existing device routing, command port 54243, display/screen targeting, context and retry deduplication:

```json
{
  "type": "command",
  "device": "*",
  "source": "controller",
  "requestId": "unique-request-id",
  "experience": "visualization",
  "command": "select",
  "visualType": "colorMap",
  "value": "Clear Blue Water",
  "screen": "Projector/gforce",
  "transitionSeconds": 1
}
```

| Command | Visual types | Value |
| --- | --- | --- |
| `select` | `theme`, `colorMap`, `waveShape`, `flowField`, `flowFieldUnion` | Exact installed name or `Random`; `None` is supported for the union |
| `next`, `previous` | All seven visual types | Omitted; alphabetical order with wraparound |
| `start` | `particle`, `sprite` | Exact installed name or `Random`; `None` clears that effect family |
| `stop` | `particle`, `sprite` | Optional exact name; omitted/empty clears the whole family |

`screen: "*"` targets all visualization screens; an omitted target uses the default display. These commands exclude media and mat screens. `transitionSeconds` overrides selection/stop timing, `delaySeconds` applies only to motion-field changes, and `durationSeconds` applies to effect starts. Particle/sprite starts retain their native fade behavior; an explicit `transitionSeconds` on an effect start is rejected rather than silently ignored. Omitted/null values use the current configuration and then G-Force's defaults. A delayed motion change is scheduled inside G-Force so it can prepare the field before switching. Commands never create a visualization screen or change configuration. Unsupported actions and unknown names are rejected; commands expire while awaiting readiness and generate no UDP replies. Accepted native actions and console diagnostics are logged with request context; an acknowledgment does not establish that every native effect has finished its transition.

See [protocol and validation notes](Visualization/GForceControlProtocol.md). `ExperienceX.Tests -- --gforce-control` covers protocol and typed-control behavior with the installed Standalone; `--visualization` covers the actual host, UDP retries/targets, live edits, fullscreen layering, crash recovery and shutdown. Tests restore vendor preferences and close owned processes.

### Renderer diagnostics

A separate one-second watchdog reads thread-safe progress counters without calling Media Foundation, DirectX or the renderer mailbox. By default, after three seconds without expected frame progress or a responsive render worker, it logs `RendererProgressStalled` once for that incident and starts diagnostics. This warning threshold follows the configured recovery timeout: two seconds earlier, bounded to 1–10 seconds. First graphics initialization and video opening have a separate twenty-second diagnostic grace period (the existing playback startup timeout remains unchanged). Idle waits, still images, minimized windows and disconnected displays do not trigger playback warnings. Restoring a display grants grace matching the warning threshold. `RendererProgressResumed` clears the warning when the stall condition ends. Screen-media locking remains unchanged.

The regular `Health` record now includes independent renderer snapshots: actual frame/present counters and ages, last known media position, media path, screen/request identity, native/managed worker thread IDs, current operation and pending command count. A stale `Playing` state alone is not treated as proof of progress.

On a stall or renderer shutdown timeout, Experience saves a JSON context snapshot and a native thread minidump under its **local runtime** `logs\ExperienceX\diagnostics` (normally `%TEMP%\Experience\logs\ExperienceX\diagnostics`). Capture uses a separate `ExperienceX.exe --capture-renderer-dump` helper before normal startup, configuration loading or single-instance acquisition; it requires no SDK or administrator prompt. The helper verifies the target's process start time, session and executable path. Dumps contain thread stacks, thread information and modules, not a full memory heap; they may still contain stack-local data and are diagnostic artifacts rather than media. They are never announced, shared or uploaded by the app.

Capture is limited to two attempts per application session, with three hostname-prefixed capture sets retained locally. It times out after twenty seconds and logs failures; a renderer shutdown timeout allows up to five additional seconds for evidence capture before exit. Existing configuration, media, firewall rules and share permissions are unchanged. Native dump limitations mean a managed heap dump or live stack trace may still be needed to identify the root cause.

`RendererRecovery` enables an independent Experience-only process restart after a persistent stall. Its settings are hot-reloaded; existing configurations that omit them use these defaults:

```json
"RendererRecovery": {
  "Enabled": true,
  "StallTimeoutSeconds": 5
}
```

The timer invokes the existing external restart script without waiting for the UI or render thread. The script validates the available build, requests a graceful exit, then force-stops an unresponsive Experience process before copying and relaunching it. Controller is not restarted. **Recovery has no attempt limit in either development or production.** Repeated stalled application instances continue requesting restart; failed script launches back off for sixty seconds and keep retrying. Only one restart is in flight per application instance. No restart-budget history file is read or written, so a prior history file cannot block recovery; existing files are left untouched as historical evidence. A completed restart depends on a valid, accessible build and restart script.

Five seconds is the default time without expected progress before requesting restart, not a promise of resumed video within five seconds. One-second timer scheduling and external staging/termination/startup add time; dump capture is best effort and does not block recovery. `StallTimeoutSeconds` accepts 1–3600 seconds and hot-reloads. An explicit hostname value such as 30 overrides the new default; change that value to 5 after installing this build to select faster recovery.

Repeated presentation-buffer waits have a five-second overall deadline. Fault/shutdown cleanup skips another presentation and attempts decoder disposal even when earlier drawing or statistics fail. Graphics ownership checks also run in Release. Drawing markers distinguish screen IDs, constant uploads, overlay texture creation, drawing, presentation, composition waits and decoder calls. Native GPU calls themselves cannot safely be interrupted inside the process; a persistent native hang requires the external restart.

`GraphicsDebugLayerEnabled` enables Direct3D validation for troubleshooting and requires an application restart when changed. Shipped Release defaults keep it off. If Windows Graphics Tools is missing, Experience logs the unavailable layer and uses the normal device. Warning/error messages are bounded and deduplicated in the application log. Use it for diagnosis rather than normal performance measurement.

`SoftwareVideoDecoding` (default `false`, restart required) selects a diagnostic software decode/processing path with cached CPU bitmaps uploaded into the existing GPU renderer. Shaders, mats and presentation remain on D3D11. Configuration, playback openings, performance records and per-screen diagnostic health identify the selected path. See [software decoding comparison instructions](Video/SoftwareDecodingDiagnostics.md) for controlled testing and interpretation; this is not an established fix for native driver lock waits.

Targeted checks: `ExperienceX.Tests -- --renderer-safety` covers presentation deadlines, production ownership checks, decoder cleanup after an injected presentation exception, unlimited repeated recovery and failed-launch backoff. `--renderer-diagnostics` blocks a real rendering worker and verifies independent detection/restart notification and subsequent progress after release. `--renderer-soak` runs three videos for one minute while repeatedly changing geometry, overlays, mats, playback and screen membership. Set `EXPERIENCEX_DIAGNOSTIC_TEST_VIDEO` to a local MP4 (a short looping clip exercises more loop boundaries). These tests use isolated windows and do not edit deployed configuration or media. They cannot establish that every driver/native failure is resolved.
